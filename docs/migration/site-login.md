# 站点自动登录与 Cookie 获取

本批按原 `SiteCookie` 的完整调用链实现 Go／React：单站／批量、可复用的原站点登录态、用户名／密码、两步码、图片验证码、原 OCR 配置及 M-Team 邮箱两阶段；手动保存 Cookie／UA 已有 Go 实现，同时修正其中未知 JSON 大整数的保留。

本批按整模块完成后集中验证。最终核心三包竞态 51 项、登录接口竞态 15 项、前端 328 项、类型检查和生产构建通过，本机与 Linux amd64 静态构建、静态检查及依赖校验通过。整库 39 个含测试包、3,384 个测试／子测试通过、退出码 0；其编译早于最后的原 HTTP OCR 配置兼容修正，修正后完整复验上述核心、接口、前端及构建，没有再次运行整库。真实 React 的登录写入和正常 Go 重启回查仍待对临时数据的明确授权，不把接口集成测试写成该项 UI 验收。

实现边界：

- 原站点与目录 LOGIN 路径、UA／代理／限流、完整配置与当前主管理员绑定；目标清单和 OCR 接收方在发送前可见，不改用其他账户或新提供方。
- 复用上一批独立 Chrome／Go 网络代理，验证码及密码仅在当前执行内存中。保留旧 `CookieUserInfo` 原配置与未知字段；新界面只写凭据，可明确选择记住用户名／密码，临时验证码不覆盖旧字段。
- 同一批请求有稳定编号，各站点独立回执；每次真实请求与浏览器登录／发邮件动作先保存意图，应答丢失、中断与重启不自动重新登录或再次发邮件。
- 只有原站点登录标记已核验、Cookie 非空，且完整来源／权限仍匹配，才事务更新原站点的 Cookie／UA。未知字段／大整数／历史保留，SQLite 静默忽略或替换不能当成功。
- 复用整理存储的跨进程 JobGuard，保护整批 Cookie 执行及旧中断记录关闭；不把超时租约当旧进程已经停止。不自动重启旧请求，关闭本地工作不冒充站点撤销登录。
- 图片验证码／两步码／邮箱和邮件码通过原编号的单次挑战传递，不进回执、日志或磁盘；源码只执行目录中固定的登录选择器，不自动点击 Cloudflare／reCAPTCHA 等验证控件。

每批最多 50 个站点，按稳定站点编号顺序处理；同一数据库由跨进程文件锁独占整个登录批次。单站最多四分钟，人工输入每阶段六十秒。普通页面预算仍为六十秒，新增的登录预算不放宽普通搜索／字幕读取。HTTP 图片只允许原站点；验证码图片经 Go 读取并回填其 Cookie，PNG／JPEG／GIF、图片尺寸和字节量都有上限。最后复核补齐 Cookie 的 Expires／Max-Age、路径及 SameSite，过期删除不作为新的会话 Cookie 留下。

## 请求与兼容入口

所有入口需要当前 Go 主管理员。写操作只在独立 Go 模式启用，查询回执不启动登录。React 提供单站入口、列表选择、目标核对、逐站结果、原编号回查、分页历史、单次验证输入及本地停止。

| 入口 | 行为 |
| --- | --- |
| `GET /api/v1/site-login` | 只读返回浏览器配置／模式／原保存账户是否完整，不返回账户信息 |
| `POST /api/v1/site-login/review` | 只读原配置，返回原站点和可选 OCR 接收方、十分钟加密审核令牌及批次编号；不连接站点 |
| `POST /api/v1/site-login/requests` | 确认原审核后创建独立回执；凭据仅随这一次 POST 传递 |
| `GET /api/v1/site-login/requests`、`requests/{id}`、`batches/{id}` | 读取原回执；网页刷新、服务重启或未知应答均不自动再次提交 |
| `POST /api/v1/site-login/requests/{id}/input` | 将有期限的单次输入交给原执行器；其他进程不能接管验证码 |
| `POST /api/v1/site-login/requests/{id}/stop` | 关闭原本地处理或持锁核对旧进程已退出后的记录，不撤回站点已收到的动作 |

旧 `/do` 的 `update_sites_cookie_ua`、`update_site_cookie_ua`、`set_site_captcha_code` 复用原生执行器；`/stream-progress?type=sitecookie` 只读输出进度／当前挑战。它们使用 Go 的主管理员令牌，不沿用 Flask 会话。旧手动 Cookie／UA 保存保留未知 JSON 大整数并核验实际写入。无 `request_id` 的相同旧批量请求固定回查原编号，Cookie 更新后及重启不变；要开始新尝试，应提供新的 `request_id`，或使用 React 的新审核。不能靠时间窗口越过未知结果再次登录。

原 `CookieUserInfo` 仍用于明确选择的保存账户来源。新 React 默认不记住凭据；明确勾选记住后，仅在全部目标成功时写入用户名和密码，其他字段（包括旧 `two_step_code`、未知大整数）保留。旧命令保留其记住账户意图，但也改为全部成功后才写入，临时两步码／验证码不覆盖旧字段，部分失败保留原账户。

原 OCR 的服务器 JSON 协议沿用 `{"base64_img":...} -> {"result":...}`。百度流程按 [官方鉴权说明](https://ai.baidu.com/ai-doc/REFERENCE/Lkru0zoz4) 的 token 及 [官方 OCR](https://ai.baidu.com/tech/ocr/general) 的 accurate_basic／words_result；两者均只在明确选择 OCR 后调用，未知应答不自动转向另一个提供方。真实服务、配额及账户未验收。

自建服务沿用原配置的 HTTP／HTTPS 地址（含原私有查询参数），不要求原 Docker 内部或局域网 OCR 先改造为 HTTPS。核对页明确显示协议／主机／路径，私有查询参数不回显；站点 Cookie 和登录凭据不转发给 OCR，不跟随服务端重定向。最后复核发现初版仅放行 HTTPS／本机 HTTP 会误拒绝原自建配置，已修正并补齐核心、HTTP 核对页及前端协议验证。

## 集中验证与剩余边界

已通过的用例包含真实隔离 Chrome 的原始字段、两步码和图片 Cookie、有效原会话复用、M-Team 邮件发送／校验三个独立动作，以及原 API 到真实 Chrome、单次验证码、SQLite 会话事务的完整链路。多站点独立成功／失败、部分结果不记住账户、其他数据库连接不能接管原登录或关闭活动执行器、旧命令回查、未知应答不重发、来源／权限撤销、SQLite 静默忽略／替换、未知大整数／BLOB 及重开也有回归。文件锁真实跨进程退出／释放由原整理存储的完整回归覆盖；模块自己的双执行器用例使用不同存储连接，不把它写成新进程证明。

集中测试发现并修正邮件码提交后读取旧输入页导致过早失败的时序问题；测试夹具也补齐 UTF-8 声明，并区分“达到请求预算不能再发请求”和“所有原请求均已确认后仍可保存结果”。验证码 Cookie 的过期补强已复验。失败轮不计通过。
