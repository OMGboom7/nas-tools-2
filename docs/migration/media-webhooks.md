# 媒体服务器通知回调

2026-10-27：Emby、Jellyfin、Plex 的通知回调接收、原消息事件映射、持久通知投递和 React 回执接通 Go。本模块替代通知链路中的临时线程，不代表所有媒体服务器事件消费者或 Python 退出已经完成。

## 原接收入口与安全范围

保留 Emby `GET／POST /emby`、Jellyfin `POST /jellyfin`、Plex `POST /plex`。三者支持 JSON；旧 Emby `data` 表单、GET 参数以及 Plex multipart 的 `payload` 字段也接入。Plex 图片附件流式丢弃，不解析为临时文件，不将附件上传到其他服务。未知子路径、方法和混合运行模式由 Go 明确拒绝，不回退 Flask，也不返回静态页面冒充接收。

入口沿用 `security.check_apikey`、原 `security.api_key` 与 `media_server_webhook_allow_ip`。启用密钥校验时，支持原 Authorization／Bearer 和唯一 apikey 查询参数；包含点的 API 密钥不误当 JWT，JWT 不能替代回调密钥。关闭旧密钥校验时保留原来源范围语义，管理页明确展示该事实；保存配置本身不会启用接收器。

只核对真实连接地址，不采用未经配置授权的转发头；IPv4、IPv6、映射 IPv4、裸地址及逗号分隔网段接通。非法字段类型、错地址族、带主机位的网段不变成“不限制来源”。原来某地址族留空的语义保留，管理页显示未限定；不静默改写现有安全配置。

新接收器默认关闭，旧媒体配置不代表 Go 执行授权。管理员须先只读审核，再分别确认接收范围、按原通知开关发送用户／设备／播放信息，以及停止旧运行时消费。纯 Go 模式同时强制检查。原管理员、配置密码／API 密钥、所选服务器完整配置、安全规则共同冻结；变化后原授权失效，添加原生授权版本不接管另一份配置。

停止接收只阻止新回调；已经提交的业务消息及通知意图保留，继续受原渠道的配置／开关核验约束。管理页说明该区别，不把停止接收说成撤回已经发送的通知。

## 实际通知内容

普通媒体新增、播放／停止、Emby 测试／登录成功／登录失败／标记事件，以及 Jellyfin 对应通知名映射到规范事件。Plex 保留原 media.play、media.stop、library.new 和电影／剧集过滤，直播及非目标事件不作为通知接收事实。其他插件原来消费的原始回调继续是独立迁移范围，不能把“ignored”当作那些副作用已执行。

按提供字段生成电影／剧集／音频标题，保留用户、客户端、设备、地址、有限剧情和播放比例；缺少季集不补造编号，运行时长为零不除零，比例限制在 0–100。Jellyfin 同时支持原 Id 和官方 ItemId、季集、客户端及 PlaybackPositionTicks 字段。原媒体服务通知开关 `mediaserver_message` 决定接收渠道。

只保存明确选取的通知字段；原回调中的服务器凭据、任意 URL、头像、媒体路径和其他未知字段不进入公开回执或消息。安全播放页面链接只用预先配置的原媒体服务器读取身份后生成，不携带服务器密钥，不跟随回调提供的 ServerUrl／thumb。媒体服务器暂时不可用时保留基础通知和固定服务图标，不伪造补全；接收不会登录 plex.tv。按媒体获取背景图、位置补全及完整旧富消息仍属于后续通知能力。

单份 JSON 上限 1 MiB、完整请求上限 2 MiB，最大 JSON 深度 20、值数 20,000、multipart 12 段、每地址族最多 256 个范围。重复键、重复消息字段、尾随文档、无效数值和超限明确拒绝，不从截断内容生成接收事实。

协议参考：[Plex 官方回调说明](https://support.plex.tv/articles/115002267687-webhooks/)、[Jellyfin 官方 Webhook 字段](https://github.com/jellyfin/jellyfin-plugin-webhook/blob/master/README.md)。Emby 兼容范围同时依据仓库原 `web/main.py` 与 `app/mediaserver/client/emby.py`，不把模拟测试称为真实服务器联调。

## 同一接收与单次发送

`GoMediaWebhooks` 保存独立原生授权版本。`GO_MEDIA_WEBHOOK_RECEIPTS` 保存每次已提交的完整规范通知、稳定编号及私有原报文摘要。原接收、`mediaserver_message` 业务事件、结构化数据和当时匹配的通知渠道在同一事务提交；没有匹配渠道也保留站内事件。配置变化、静默忽略写入或关键结果被触发器修改时整组回滚。

同一原授权内，发送方提供 EventId／NotificationId 或显式 `X-NASTool-Event-ID` 时，原报文的规范摘要与稳定编号共同约束重复接收；相同编号、相同内容只查回原事实，不重新建立渠道或发送意图。相同编号但内容变化拒绝，不采用新内容覆盖旧事件。原业务证明损坏也不能虚报重复接收成功。

没有唯一编号时，每次获得新编号，不用内容或时间窗口猜测去重，避免丢弃合法的再次播放。换接收授权版本属于新的接收范围，不能据此宣称跨版本或所有上游都具备 exactly-once 投递。

通知复用原持久发送器：当前渠道仍与接收时完整摘要一致，才先写 sending 并调用一次原生渠道发送操作；修改／删除／停用渠道不能接管旧消息。该次调用应答丢失、网络异常、进程中断及结果写回丢失后，后台不重新调用发送器，也不重放原回调。原渠道适配器仍可能内部分段、上传图片或降级成文本；本批一次模拟 Webhook 请求不能证明所有渠道只有一次 HTTP 请求或端到端 exactly-once，完整图片／分段协议继续验收。接收成功、渠道确认、媒体入库与播放完成是不同事实。

原稳定编号查询关联到原完整通知渠道回执，不受站内消息最近 50 条限制。列表每页 30 条，支持较早回执；渠道 ID 以十进制字符串返回，超过 JavaScript 安全整数仍保持精确。只读接口不创建接收授权／回执表、不查询媒体服务器、不发送消息。

## 管理界面与接口

通知页新增接收管理及原回执查询，原业务消息面板同时采用可读的深色按钮样式。每次重新审核、操作后和会话切换都会清除独立确认；不自动轮询或重发。设置应答丢失后只允许读取当前状态；稳定编号一直用于查询原事件，不因页面刷新重新接收或发送。

- `GET /api/v1/media-webhooks`：当前原配置及授权审核，不返回密钥或私有范围摘要。
- `POST /api/v1/media-webhooks/authorize`：新审核指纹与三项独立确认，保存新的接收授权。
- `POST /api/v1/media-webhooks/stop`：明确确认后停止新接收；服务器当前不可用也可停止，旧回执保留。
- `GET /api/v1/media-webhooks/receipts?page=1`：本页最多 30 条完整原回执。
- `GET /api/v1/media-webhooks/receipts/{id}`：按稳定编号关联原业务事件与全部冻结渠道的发送事实。

管理接口要求当前管理员与纯 Go 模式；公开回调按自己的原密钥／IP 规则鉴权。未迁移插件不会因为收到回调而启动，回调不能直接授权删除媒体、停止／删除种子或改变限速。
